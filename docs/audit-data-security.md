# Career Quest: аудит данных, прогресса, HR и разграничения прав

**Статус:** ниже сохранены исходные находки до исправлений. Исправления и результаты повторных проверок описаны в [audit-data-security-fixes.md](audit-data-security-fixes.md). Скрипт `audit/data-security-probes.cjs` теперь проверяет исправленное поведение; прежний JSON результатов сохранён отдельно.

Дата: 2026-09-23. Основание: приложенный пользователем текст ТЗ, раздел Career Quest. Проверка выполнена без изменения продуктового кода. Изолированный скрипт проверяет реальные parser/domain/application функции без БД; дополнительно изучены результаты HTTP-проверки основного аудита: [audit-runtime-results.json](audit-runtime-results.json). Где HTTP и чистые функции проверялись на разных профилях, результаты разделены.

## Подтверждённые дефекты

### DS-1 — высокая: активность после отказа остаётся доступной, но повторно выполнить её нельзя

**Место:** `backend/src/modules/development/application/development.service.ts:49–53`, `backend/src/modules/development/domain/policies.ts:36–38,51–58`.

Для неповторяемого курса используется единственный ключ участия `once`. При повторной записи `register()` без проверки статуса возвращает старое участие. При этом eligibility исключает только завершённые и активные участия: `declined`, `dropped`, `no_show` снова считаются допустимыми. Все три состояния являются терминальными и перейти из них в `completed` нельзя.

**Воспроизведение:** зарегистрировать неповторяемый полезный курс → отказаться (или начать и бросить) → снова запросить доступные активности → повторно записаться. В тесте реального DevelopmentService результат для всех трёх статусов: `listedEligible=true`, `newRegistrations=0`, возвращён прежний terminal status, завершение отклонено. HTTP-проверка подтверждает для `declined` и `dropped`: `eligibleAgain=true`, повторный POST возвращает 201 и то же участие в terminal status, завершение возвращает 409 `INVALID_TRANSITION`.

**Граница доказательства:** в обоих проверенных HTTP fixture-профилях `recommendedAgain=false`: именно этот курс не вошёл повторно в top 3. Eligibility допускает его в кандидаты рекомендаций, и проблема затронет рекомендацию, если ранжирование выберет курс. Обязательное повторное попадание в top 3 данным тестом не утверждается.

**Влияние на ТЗ:** доступный в каталоге шаг невозможно выполнить после добровольного отказа. Особенно заметно на повторном показе демо и при попытке «передумал, всё-таки пройду»; возможен также выбор такого шага рекомендациями при другом составе кандидатов.

**Исправление:** отделить попытку от ограничения «успешно завершить не более одного раза»; создавать новую попытку после terminal unsuccessful состояния либо явно согласовать eligibility и политику запрета. Успешные завершения по-прежнему защищать от двойного gain.

### DS-2 — высокая для HR-сценария: брошенные активности не приводят к попаданию в «нуждается во внимании»

**Место:** `backend/src/modules/hr-analytics/application/hr-analytics.service.ts:47–60` (особенно 55–57); `backend/src/modules/hr-analytics/presentation/hr-analytics.dto.ts:14`.

Проверяются только отсутствие записей и статусы `NO_SHOW`/`SKIPPED`. `SKIPPED` исходная schema не принимает; реальные `DROPPED` и `DECLINED` не учитываются.

**Воспроизведение:** сотрудник с достаточными входными данными и доступным следующим курсом, четыре участия одного типа в окне. Для четырёх `DROPPED` — список attention пуст; для четырёх `DECLINED` — пуст; замена на `NO_SHOW` — одна запись с `REPEATED_SKIPS_IN_WINDOW`.

**HTTP-подтверждение:** основной аудит импортировал по три `DROPPED` и `DECLINED` для отдельных новых профилей, оба импорта вернули 201 `APPLIED`; запрос HR attention вернул 200, оба профиля отсутствовали (`threeDroppedVisible=false`, `threeDeclinedVisible=false`).

**Влияние:** сотрудник, бросивший всё обучение, исчезает из ключевого HR-среза. Отказы требуют более осторожной интерпретации: это сигнал неподходящего предложения, а не «плохой сотрудник»; ТЗ отдельно требует добровольности. Но отсутствие различимого сигнала вообще лишает HR требуемой информации.

**Исправление:** отдельные прозрачные признаки repeated drops / repeated declines / длительно незавершённое участие, не объединять причины с мотивацией или прогнозом увольнения. Счётчики и окно показать явно.

### DS-3 — средняя: JSON `null` роняет parser вместо диагностического отказа

**Место:** `backend/src/modules/dataset-import/infrastructure/parsers/dataset.parser.ts:13,31–44,54`; `backend/src/modules/dataset-import/application/import.service.ts:17–18`.

Schema фиксирует ошибку, но затем парсер без проверки вызывает `unknownFields(null, ...)` и `Object.entries(null)`. Ошибка возникает до создания ImportRun с диагностикой.

**Воспроизведение:** `parser.parse({'employees.json': Buffer.from('null')})` → необработанный `TypeError: Cannot convert undefined or null to object`. Аналогично `skills.json`, `events.json`, `dataset-rules.json`. Это syntactically valid JSON, но неправильный dataset; ожидается безопасная ошибка валидации.

**HTTP-подтверждение:** загрузка `null` в `employees.json`, `skills.json` и `events.json` дала 500 `INTERNAL_ERROR`; JSON rules отдельно проверен только на уровне parser.

**Влияние:** неверный файл на защите превращается в серверную ошибку, нормальный отчёт импорта теряется. Перезапуск сервера не требуется; фактов изменения бизнес-данных этим тестом не обнаружено. Доступ к HTTP импорту ограничен HR, поэтому это не обход авторизации.

**Исправление:** извлекать metadata только из валидного object-wrapper либо проверять объект и `null` до `Object.entries`.

### DS-4 — средняя: история до даты найма принимается при history-only импорте

**Место:** `backend/src/modules/dataset-import/application/validate-import.ts:36–37`; `backend/src/modules/dataset-import/infrastructure/prisma-import.store.ts:20,24`; `backend/src/shared/application/dataset-contracts.ts:19`.

Hire-date проверяется только у сотрудника из текущего `plan.employees`. У уже существующего сотрудника `ExistingImportState` вообще не содержит hireDate.

**Воспроизведение:** E0001 принят на работу `2026-04-28`. Новая строка `declined` датой `2000-01-01` с существующими employee/event ID: отдельно в `activity_history.csv` результат `valid=true`; та же строка вместе с неизменённым профилем — `valid=false`, `INVALID_DATE`.

**HTTP-подтверждение:** отдельный history-only dry-run с записью до найма вернул 200, `status=VALIDATED`, `valid=true`, одна запись к созданию. Эта HTTP-проверка была dry-run и не доказывает сохранение конкретной записи; дефект допуска данных проверкой подтверждён.

**Влияние:** обязательный частичный импорт истории имеет менее строгую проверку, чем полный. Такие данные попадают в историю рекомендаций; ранжирование не ограничивает history определённым временным окном.

**Исправление:** включить hireDate существующего сотрудника в состояние проверки и применять единый инвариант независимо от комплекта файлов.

## Дополнительные ограничения и ловушки защиты

1. **Идентификаторы 129–200 символов:** schema импорта принимает `event_id` длиной до 200 (`dataset.schemas.ts:2,10`), endpoint регистрации разрешает `activityId` только до 128 (`development.controller.ts:12`). Такая импортированная активность видна, но зарегистрироваться через HTTP нельзя. Низкая вероятность на штатном датасете; статически подтверждённая несогласованность контрактов, HTTP отдельно не запускался.
2. **Повторный профиль с тем же ID:** изменённые skills/last_review_date намеренно отклоняются как `BASELINE_CONFLICT` (`validate-import.ts:23`), отдельного reassessment workflow нет. Дополнительные новые профили поддерживаются; если жюри перезаписывает существующие E00xx, сценарий требует заранее определённой политики и отдельной чистой БД. Это документированное ограничение, а не автоматическое нарушение must-have.
3. **Дополнительная завершённая история после online-прогресса:** в `last_review` режиме даже позднее по дате завершение отвергается при `onlineVersion>0` (`validate-import.ts:45–47`). Это защита ledger, но она ограничивает живое пополнение истории. Старые записи до baseline и новые сотрудники обрабатываются отдельно.
4. **Новые учётные записи:** seed создаёт только одного demo HR и одного employee (`backend/prisma/seed.ts:11–16`). Импорт нового профиля не создаёт логин; новый профиль доступен HR, но полноценная выдача каждому сотруднику личного доступа не реализована через публичный API. Для защиты нового профиля в HR этого достаточно, для полного employee self-service на новых профилях нужен provisioning.
5. **Семантика baseline взята из внутренних документов проекта:** `backend/docs/data-contract.md:27–31` утверждает `last_review`, missing skill=0 и допущение по дате self-paced. README оригинального стартового кита в проверяемых файлах не обнаружен, поэтому математическая согласованность подтверждена, но точность интерпретации исходного README независимо не подтверждена. Не считать это найденной ошибкой формулы.
6. **Разные наборы в репозитории:** полный 200/40/60 dataset есть в `frontend/app/data`, а default compose использует маленький fixtures-набор 6/8/4. Наличие полного набора на диске не означает его загрузку при обычном запуске. Главный аудит должен отдельно подтвердить запуск и демонстрацию полного объёма.

## Что прошло и почему это существенно

- 5863 комбинации current/gain/cap не нарушили монотонность, общий cap 5 и локальный cap; когда текущий уровень уже выше cap, он не уменьшается.
- Дополнительный профиль с новым ID принимается относительно существующих ролей/навыков/каталога.
- Все 3075 записей полного набора (60 навыков + 32 role-grade + 200 employees + 40 events + 2743 history) проходят parsing и cross-reference validation.
- Доменная проверка разрешает employee свой профиль, запрещает чужой, разрешает HR. В HTTP guard JWT проверяется HS256 с issuer/audience; роль берётся из БД, а не из присланного JSON/JWT role claim (`auth.guard.ts:18–28`).
- Import и HR endpoints требуют HR. Participation endpoints проверяют employee scope и принадлежность participation сотруднику.
- Пароли хешируются scrypt с солью, сравнение constant-time (`credentials.ts:8–19`); внешняя передача LLM по умолчанию выключена.
- Mandatory исключены из AI рекомендаций (`policies.ts:31`), будущую сессию нельзя завершить (`development.service.ts:104–105`), unknown skill не превращается в выдуманный gain (`policies.ts:6`).

## Воспроизведение

Из `backend/`:

```powershell
node -r ts-node/register/transpile-only ../docs/audit/data-security-probes.cjs
```

Первоначальный запуск завершился с кодом 0 и вывел 15 наблюдений неправильного поведения; они сохранены в `audit/data-security-probe-results.json`. После исправлений скрипт обновлён: теперь assert-проверки требуют корректного поведения, а результат записан в `audit/data-security-fix-results.json`. Скрипт не запускает БД, серверы, контейнеры или внешние LLM и не меняет исходные файлы датасета.

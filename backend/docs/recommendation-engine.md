# Recommendation engine

Pipeline: Development application contract → full-catalogue bounded sequence planning → optional real model choice among verified plans → plan/evidence validation → server-rendered sequential effects and comparison → version-checked persistence. GET latest never invokes the model. Generation returns 0–3 items and one of READY, DATA_INCOMPLETE, NO_NEXT_GRADE, NO_ELIGIBLE_ACTIVITIES. Empty output never invents an activity or triggers an unnecessary model request.

## Rules and evidence

`sequential-plan-v3` and `verified-plan-selection-v3` invalidate older saved sets. The planner evaluates sequences, not a greedy list of individually ranked courses. For example, at level 1 with target 4, a +1 course capped at 2 must precede a +2 course capped at 4: 1→2→4. Taking the bigger course first would leave level 3. The planner searches these orders and the model validator no longer rejects the first course using isolated one-step Pareto comparisons.

The transparent plan score is 70% fraction of weighted next-grade gaps closed, 15% mean observed history fit, 5% mean explicit feedback, 5% novelty and 5% role fit. Critical gaps have weight 2; prerequisite-only gains do not count as grade-gap closure. Duration is an explicit metric and a tie breaker. This remains an engineering heuristic, not a learned probability or proof of engagement benefits. Atomic candidate scoring remains available for eligibility/legacy evaluation and initial deterministic ordering; production selects the complete plan. No unsupported causal weight is assigned to tenure or unknown work format.

Search covers all sequences of up to three distinct activities for the supplied 40-event catalogue. Skills, prerequisites, caps and date availability are re-evaluated at each step. Catalogue prerequisites can justify a preparatory course that has zero immediate next-grade effect; such a course is retained only if a later selected activity needs it. Its evidence is explicitly `PREREQUISITE_GAP`, `requirementType=ACTIVITY_PREREQUISITE`, with the affected activity IDs, never a fabricated grade requirement. Final plans must deliver a positive actual grade-gap reduction.

Dates have day precision. A self-paced step starts no earlier than the planning cursor; a scheduled step uses the earliest catalogue session on or after it. The next step starts no earlier than `start + max(1, ceil(durationHours / 24))` calendar days. This conservative minimum-time forecast prevents reversed sessions and same-day overlap without inventing an eight-hour working day. It is not a booking, a verified completion time, or evidence that the employee is available. Long self-paced learning may take longer in reality; regeneration after completion uses the actual current profile.

Search attempts are capped at 100,000, fairly divided among all initially feasible first steps so that late catalogue entries are not hidden by a top-10 cutoff. The supplied 40-event catalogue fits this count bound. CPU search also checks an explicit wall-clock deadline (default five seconds, reduced to the remaining request budget); an async timeout alone cannot interrupt synchronous search. Truncation reports `diagnostics.planning.complete=false`; exhausting time before any feasible result returns `503 PLANNING_DEADLINE`, not a false no-activities claim. Proposals retain the best continuation for each first activity at each step count (at most 120 for 40 activities). History is computed once per catalogue activity during a plan search. HR's bulk eligibility projection keeps its existing lightweight path.

History compares completed, skipped/no-show, declined and **dropped** outcomes from **self-assigned nonmandatory** learning. Manager/HR assignment does not establish either consent or reluctance: these records are counted separately and excluded from preference fit. Exact skill overlap is strongest; different skills with an explicit matching catalogue category use a weaker 0.25 match, disclosed in `categoryMatchedRecords`. Mandatory and unrelated learning, active registrations and future records do not establish a preference. Matching format weighs 1 versus 0.25; matching activity type 1 versus 0.5; participation-date recency has a 180-day half-life. Fit is `(weightedCompleted + 1) / (weightedCompleted + weightedUnfinished + 2)`.

Evidence includes raw counts, weighted totals, assigned-record count, scope, half-life and `dateBasis=PARTICIPATION_DATE_NOT_COMPLETION_TIME`. The source date is not relabelled a completion timestamp; the engine does not claim an activity was completed on time. Dates remain relative to the original observation cutoff throughout a forecast, not to a hypothetical future course date. These weights are explicit modelling assumptions, not fitted behavioural probabilities. `NO_RELEVANT_HISTORY` distinguishes existing but incomparable/assigned history from no recorded history; both are unknown/neutral 0.5. Repeated non-completion softly favors another approach without prohibiting the skill or diagnosing motivation.

The next grade and its requirements come from the role-specific catalog order. No recommendation is generated when target requirements or any required level are unknown. This conservative DATA_INCOMPLETE policy avoids silently treating missing knowledge as zero. Reaching the final grade yields NO_NEXT_GRADE. Activities with an invalid audience, prerequisites, unavailable sessions, prohibited repeats or no useful relevant gain are excluded with reasons. All effects use the development module policy. Later steps are forecast after earlier steps; caps and requirements already satisfied are respected.

Each candidate contains server-created evidence IDs: career context (`career`), concrete gap (`gap:activity:skill`) and history (`history:activity`, including explicit absence/unknown evidence). Internal `LlmInput` includes all discovered candidates and `plans`: verified activity sequences, per-step evidence IDs, chronological dates, total weighted/critical gap reduction, hours and contextual metrics. For v3, the provider returns only `{"planId":"…"}`. Structured Outputs restricts that ID to the enum of offered nondominated plans. The adapter maps it to the existing internal `activityId`/`evidenceIds` contract using the exact server-owned plan; the model does **not** author these evidence IDs. Redundant per-plan evidence IDs and translated skill names are omitted from the provider payload. Zod rejects extra fields, unknown IDs and malformed JSON. The full sequence and mapped facts are validated and replayed against authoritative context before materialization.

Whole-plan Pareto validation rejects a plan only when an offered alternative has no worse weighted/critical closure, history, feedback, novelty and role fit, with no greater duration or step count and no later forecast finish, and is strictly better on a measured dimension/cost. An immediately available course can therefore remain a genuine trade-off against a larger later session. The model is not forced to copy the heuristic ordering. Failures are labelled `LLM_UNVERIFIED_PLAN` or `LLM_DOMINATED_PLAN` and use the valid rules plan. Adapter inputs without `plans` remain supported for older isolated contract tests, but production always supplies verified plans.

Gap evidence is created at each step's actual forecast state, never retained from an earlier level. `SEQUENCE_CONTEXT` records estimated dates and their assumption. `PLAN_COMPARISON` shows a different feasible plan's actual weighted closure, duration and history fit alongside the selected plan, so an explanation supports comparison rather than merely listing why an activity is eligible. Comparison metrics come from the server, never model prose. Localized ru/kk/en templates render verified facts with skill names, criticality and final levels; IDs stay stable. Catalogue translations fall back to English/original names.

## Model integration and privacy

Default `LLM_PROVIDER=disabled` returns RULES_FALLBACK, `aiUsed=false`, `fallbackReason=LLM_DISABLED`. A fake transport in tests is not live AI. OpenAI integration uses HTTPS POST `/v1/responses`, `store:false`, `text.format.type=json_schema`, strict schema, no tools and no SDK retries. Refusal and incomplete output are detected. API source checked: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) and [Responses migration guide](https://developers.openai.com/api/docs/guides/migrate-to-responses).

External requests require `ALLOW_EXTERNAL_LLM=true`; an API key alone does not authorize transmission. Default tests make no external calls. A request contains catalogue candidates, verified plan summaries, relevant requirement facts and aggregate history for one anonymous profile, never employee names, emails or the full employee array. Treat catalogue strings as untrusted data; system instructions prohibit following instructions embedded in them. Redirects are rejected so a loopback endpoint cannot redirect to an external service.

`LLM_PROVIDER=local` implements the native Ollama API; arbitrary OpenAI-compatible endpoints are not assumed compatible. Set `LLM_BASE_URL=http://127.0.0.1:11434` (the default local URL) and `LLM_MODEL` to an already downloaded local model. Start Ollama and download the chosen model before starting the API; model download and warm-up are not hidden in a recommendation request. The protocol is:

1. `GET {LLM_BASE_URL}/api/tags` must list the configured model.
2. `POST {LLM_BASE_URL}/api/show` with `{model,verbose:false}` must expose completion capability and model metadata. Without external permission, inventory and metadata must have no remote_host/remote_model, the model must have positive local size, GGUF format and nonempty model_info. Cloud suffixes are rejected before any request. Missing metadata fails closed before career context is sent.
3. `POST {LLM_BASE_URL}/api/chat` receives `{model,stream:false,messages,format:<JSON schema>,options:{temperature:0,num_predict:256}}` for v3 plan selection. The adapter requires `done:true`, a complete message.content, and validates `{"planId":"…"}` against the offered IDs. Legacy inputs without plans retain the prior `recommendations` contract and 1500-token ceiling. A plan maps to at most three unique activities with server-derived evidence references.

Sources checked: [Ollama chat API](https://docs.ollama.com/api/chat), [model inventory](https://docs.ollama.com/api/tags), [official metadata types](https://github.com/ollama/ollama/blob/main/api/types.go). Runtime capability checks do not assert that every local model follows the schema: invalid answers fall back to rules. Model-server responses are limited to 256 KiB. Use a trusted local Ollama process; the backend cannot attest the execution internals of a malicious server.

Without external permission the hostname must be exactly `127.0.0.1`, `[::1]` or `localhost`. Under Compose these addresses mean the API container itself. To use a separate service hostname, an operator must explicitly set the external-transfer permission after reviewing that service. The provider URL is server configuration, never a request parameter.

The default model timeout is 5 seconds, maximum configured 6 seconds; AbortSignal cancellation covers capabilities, network and response parsing. An outer 10-second deadline covers the full use case, aborts model requests and prevents subsequent writes after a delayed context read. The final database transaction timeout and queue wait fit the remaining budget. If storage cannot provide a consistent persisted response in that budget, HTTP 503 RECOMMENDATION_DEADLINE is returned; no unsaved result is presented as persisted. Database contention and deployment latency still require end-to-end measurement. Provider failure, timeout, refusal or invalid output returns an explicit rules fallback while storage remains available.

## Persistence and freshness

Context version covers profile, current skills, history, feedback, global catalog (including requirements) and availability as-of date. The cache key additionally includes employee, language, provider/model, ranking and prompt versions. TTL is 15 minutes. JSONB key ordering does not affect version equality. Profiles, history, feedback, requirements or catalog changes invalidate saved recommendations. No transaction is held while awaiting an LLM. The context is re-read afterward; any change discards model output and computes current rules. A short final PostgreSQL transaction locks version owners and checks the same versions before saving. A conflict retries once using current rules.

Snapshots retain numeric context, catalog effects and restrictions, feedback preferences and compact history without the employee name, sufficient to reproduce the ranking policy. User feedback is employee-owned, checks the set/activity relationship and increments feedbackVersion atomically. Latest feedback for an activity changes its preference component. General set feedback is stored and invalidates context without guessing which activity was disliked. A cached fallback can be reused until TTL; POST with `force:true` retries the configured provider immediately. Serialization conflicts or deadlock victims trigger one rebuild using current rules; continuous concurrent mutation returns an explicit conflict rather than stale AI.

## HR projections

HR uses one read-only Repeatable Read projection across module-owned tables, an explicit documented boundary exception. It does not invoke the model. Skills are grouped by skill, role, current grade and next grade. Unknown skill levels have their own count and never become zero. Deficit share and mean gap use only known levels with applicable requirements; applicable population and incomplete counts are separate. Participation rates divide completed records by all actual participation records within the requested window; unique participants are counted separately.

Default history window ends at the dataset `asOfDate` (or configured AS_OF_DATE) and starts 365 days earlier, both dates inclusive. Dates are not rewritten. The as-of date controls activity availability and the default reporting window; skill levels represent current application state, not a reconstructed historical skill snapshot. Use dateFrom/dateTo explicitly for current online activity outside the historical demonstration window. Signals for missing next steps, incomplete data, no recorded participation and repeated skips are observations, never motivation diagnoses or attrition predictions.

Coverage separates NOT_GENERATED, FRESH, STALE, NO_ELIGIBLE_ACTIVITIES, DATA_INCOMPLETE and NO_NEXT_GRADE. Live eligibility is computed independently of whether any recommendation was ever generated.

## Evaluation

The original v2 evaluation used eleven synthetic fixtures; those saved results describe the previous engine and do not validate v3 by themselves. The current evaluator adds bounded-plan traps and an independent small-catalogue arithmetic oracle. Compare identical step budgets, report actual step count and hours, and distinguish evidence correctness, first-choice regression expectations, achievable gap reduction and cost/history trade-offs. A source-generated expected first ID is not jury-set accuracy.

Evidence verification must advance authoritative skill state and chronological availability, distinguish actual grade requirements from real catalogue prerequisites, and verify the comparison plan as well as the selected plan. It must not merely count three factor categories or trust agreement between two output fields. Its scope is structured factual correctness; it cannot establish that the history weights are pedagogically optimal or that the model improves employee engagement.

Live evaluation requires explicit opt-in, provider configuration and external-transfer permission. It must report actual provider calls, model use, timeouts and fallback separately. The separate `test/evaluations/llm-live.spec.ts` is opt-in. Unit adapter tests use deterministic HTTP fakes and are labelled mocked. Pure planner latency is not HTTP/PostgreSQL latency. Passing the small regression set does not substantiate LLM superiority, engagement gains or accuracy on unknown jury profiles; these claims require a held-out independently judged evaluation.
